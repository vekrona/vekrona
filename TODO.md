- Quickshell never reconnects an I3 event socket that Sway closes. `I3Ipc::eventSocketStateChanged` (`src/x11/i3/ipc/connection.cpp`) only logs `I3 event socket disconnected.` (or `I3 socket error: QLocalSocket::PeerClosedError`); the only reconnect is `reconnectIPC()`, called on a frame without the `i3-ipc` magic, which Sway never sends. Every `I3IpcListener` (Keyboard, Windows) owns its own `I3Ipc` and has no `connected` signal, so QML cannot even see the loss. Shown in vekrona-dev on 2026-11-04: with the shell behind the relay of `tests/e2e/sway-ipc-gap-proxy.py` and that relay killed and started again at the same path, the shell logged `PeerClosedError` and then never saw another window: a new window was in Sway's tree but `qs ipc call appswitch apps` kept listing the old set (the switcher, the window list and the keyboard pill all go stale until `systemctl --user restart vekrona-shell`). Not caused by a Sway reload: `swaymsg reload` and the shell's own `SwayConfig` reload leave the sockets up, and events still arrive afterwards (checked by opening and focusing windows). What would make Sway close a subscriber is unverified (candidates: Sway drops a client whose write queue is too long; the comment in `SwayQuery.qml` says Sway drops IPC connections across sleep). Next: find out whether Sway ever closes event sockets on resume or under load (check the journal after a suspend on the host for `I3 socket error`); if it does, patch Quickshell to reconnect on `UnconnectedState` while it was connected (and re-emit `connected` so `SwayQuery` re-queries), or restart the shell from a QML watchdog; the simplest stopgap in our QML is to rebuild each `I3IpcListener` (a `Loader` toggled off and on) after resume.
- A vekrona-shell that hangs (alive, not crashed) while the app switcher is open leaves Sway in its `appswitch` mode, and nothing resets it: `ExecStopPost=-/usr/bin/swaymsg mode default` in `vekrona-shell.service` runs only when the process exits, and the mode deliberately has no Escape or Return binding, so those keys reach the overlay. Resetting the mode alone would not rescue the session anyway: the hung overlay keeps its exclusive layer-shell keyboard focus, so typing still goes nowhere. Why it matters: the keyboard is dead until the shell is killed from another VT or over ssh. No clean fix found: binding Escape in the mode to `mode default` plus `exec qs ipc call appswitch cancel` frees the bindings but not the keyboard focus, and a systemd watchdog needs a periodic heartbeat from QML, which is a wakeup we do not want on battery. Next step: decide whether an always-available Sway binding (in the mode and in `default`) that restarts `vekrona-shell.service` is the escape hatch, since it covers every hung shell surface, not just the switcher.

- Sync, laptop power. Measured 2026-11-05 in the vekrona-dev guest (Syncthing 2.1.6, idle, one paired peer in a network namespace on a veth pair; 10 minutes per row after a 90 s warm-up; the unit's main process is Syncthing's monitor and the work is in its child, so both are counted; "wakeups" are context switches of all their threads; WAN is the guest's network interface, whose background traffic is 37.5 packets and 2.8 KB a minute with Syncthing stopped; `vekrona-sync watch` itself had 0.00 wakeups a second in every row; CPU is under 20 ms a minute in every row; single runs, so about 3 wakeups a second and 8 packets a minute are noise; the tool and the scripts are in ~/.cache/sync-verify/final/). Defaults here: `reconnectionIntervalS` 20, `relaysEnabled`, `natEnabled` and `globalAnnounceEnabled` on, `stunKeepaliveStartS` 180.

  | peer | change | wakeups/s | WAN packets/min | WAN KB/min | Syncthing connections off the LAN |
  |---|---|---|---|---|---|
  | none (Syncthing stopped) | control | 0 | 37.5 | 2.8 | 0 |
  | connected | defaults | 15.8 | 58.5 | 6.3 | 3 |
  | connected | `relaysEnabled` off | 15.7 | 42.7 | 4.8 | 3 |
  | connected | `natEnabled` off | 15.7 | 43.7 | 4.9 | 4 |
  | connected | `globalAnnounceEnabled` off | 18.8 | 50.1 | 5.5 | 3 |
  | connected | `stunKeepaliveStartS` 0 | 14.8 | 43.5 | 4.9 | 3 |
  | offline | defaults | 17.9 | 50.1 | 5.6 | 1 |
  | offline | `reconnectionIntervalS` 600 | 18.0 | 50.9 | 5.7 | 1 |
  | offline | relays, NAT and global announce off | 11.3 | 29.3 | 5.0 | 0 |
  | offline | those three off and `reconnectionIntervalS` 600 | 11.8 | 24.1 | 3.1 | 0 |

  What it says: Syncthing costs little in CPU, but its wakeups are 11 to 18 a second, and no knob takes them below about 11 (Go's runtime and the scan and event threads). A single knob moves the wakeups and packets by about the noise; relays, NAT and global discovery together take the offline-peer case from 18 to 11 wakeups a second (a third less), from 50 to 24-29 packets a minute, and close the connection to the relay and the discovery server. `reconnectionIntervalS` showed nothing, because the other device here has only a LAN address, which is refused at once; a phone that is away has relay and global addresses, so each 20 s retry costs a discovery lookup and a relay attempt that this setup does not make, and the real saving of a longer interval is bigger than measured. Local discovery's announcement (every 30 s, no option for the interval) is about 2 LAN packets a minute and is what Nearby and QR-less pairing need. Not measured: a laptop on a real network, a phone that is away, and powertop (not in the guest).

  Recommendation for laptop defaults, not applied (the energy rule: pick the lower-power option and let the convenience recover on demand): `relaysEnabled` false, `natEnabled` false (which also ends the STUN keepalives, so `stunKeepaliveStartS` needs no change) and `globalAnnounceEnabled` false, with `reconnectionIntervalS` 300. Keep local announce on: it costs about nothing and the pairing popout depends on it. The trade-off: with these off, a device that is not on the same network (a phone on mobile data, a friend's device) cannot be reached, because Syncthing then has no relay to meet at and no discovery server to learn an address from, and an offline device is retried every 5 minutes instead of 20 seconds, so a phone that comes home syncs up to 5 minutes later. The convenience should come back on demand: a "Sync away from home" switch in the popout that sets the three options and a 20 s interval for as long as the user wants it (and sets them back when the popout's switch is turned off or the laptop suspends), and the popout opening could ask Syncthing to dial the devices at once. The host has Tailscale: a device on the same tailnet can be given a fixed address (`tcp://<its tailscale name>:22000`; Syncthing listens on the tailscale interface already), so for devices on the tailnet the relays, global discovery and NAT mapping are not needed at all, and the switch above would only be for devices that are not on it. That needs vekrona-sync to write the tailnet address into the device (`pair` knows the ID only) and the phone to run Tailscale; decide whether vekrona wants to depend on it.

- Sync, Syncthing's own configuration changes: `Syncthing.edit_config` in `bin/vekrona-sync` serializes every change from vekrona-sync under one lock and reads what it changes under it, but Syncthing changes its configuration by itself too (a device's name when it first connects, an introducer's devices), and a PUT that read the configuration just before such a change undoes it. - Sync, Nearby keeps devices that left: sync.json lists every device in Syncthing's discovery cache (the 16 reported last), and the cache never forgets one. A time window on Syncthing's DeviceDiscovered event cannot prune it: Syncthing announces every 30 s, but it emits DeviceDiscovered only when a device is new, was silent for more than 90 s (`CacheLifeTime`) or restarted (`registerDevice` in `lib/discover/local.go`, Syncthing main, 2026-11-05), so a device that stays on the network is reported once and would be pruned while it is there.
