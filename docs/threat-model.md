# Threat model

What vekrona protects, from whom, and where it deliberately does not. It is one laptop or
desktop with one user. The user is trusted; the things that run as the user are not all.

## What is not defended

A process that runs as you can do what you can do. vekrona runs Steam games, Firefox,
Flatpaks, coding agents and shell scripts as one Unix user, with no sandbox between them,
except where a row below says so. So malware that already runs as you can read your files,
use your Wayland session and take what an unlocked keyring hands out. The boundaries below
keep that malware out, or keep less valuable things from becoming such a process.

## Trust boundaries

| Boundary | Who is on the far side | What holds it |
|---|---|---|
| Local processes and the loopback network | Other users' processes, sandboxed apps that share the network, any program that can open `127.0.0.1` | Syncthing's GUI and REST API listen on a unix socket, `/run/user/<uid>/syncthing/gui.sock` (the address in its `config.xml`, so any start of the daemon gets it), in a directory only the user can enter (`RuntimeDirectory=syncthing`, mode 0700), and on no TCP port: nothing listens on `127.0.0.1:8384`, so no other user's process, no sandboxed app that shares the network and no web page in Firefox can reach it. The socket has no login: the OS user is the authentication. vekrona has no OS sandbox, so a process of the same user, a coding agent included, can open the socket and reconfigure the daemon, just as it could read the password file that this replaces; the boundary is the same user as before, and no gate against a same-user process is promised. vekrona runs no sshd: stage 30 removes `openssh-server`, so no remote shell listens on any address. (The vekrona-dev VM and the ISO test guest carry the marker `/etc/vekrona/keep-sshd` and keep sshd, because their host drives them over ssh; that is a test guest, not a machine you use.) |
| Journal to coding-agent prompt | Whoever can get a line into a log: a web page through a webapp, a file name, a peer on the network | `vekrona-error` copies journal text into `context.txt` and the prompt it hands the agent. The `vekrona-diagnose` skill says all of it is data, never instructions. Agents run with their default permission prompts: the launcher passes no auto-approve flag, and the managed policy switches Claude Code's bypass mode off. Read each prompt before you approve it. |
| Coding agent to your secrets | A manipulated or mistaken agent | `/etc/claude-code/managed-settings.json` denies Claude Code's file tools `~/.ssh`, `~/.gnupg`, the login keyring, the calendar config, agent credentials, Syncthing's config and keys, and Firefox logins and cookies ([agents](agents.md#installing-a-harness)). This covers its file tools and the file commands it recognizes in a shell command, not a script it writes and runs, and there is no OS sandbox: it slows a manipulated agent down, it does not box it in. Codex, OpenCode, Pi and Cursor have no such policy. |
| Webapps | The sites behind Telegram, Discord, Spotify, SoundCloud, YouTube, WhatsApp | Each runs in its own Firefox profile (`vekrona-<app>`), so cookies and logins are not shared with your browser or with each other, and Firefox's content sandbox contains the page. One enterprise policy (`config/firefox/policies.json`) turns telemetry and studies off, skips the welcome pages, turns tracking protection on and prelaunches one content process instead of three (about 160 MiB of RAM per instance) for every profile. A webapp is not a VM: a Firefox exploit runs as you. |
| Lock screen and security key | Someone at your machine | The lock (`vekrona-lock`) takes your security key with its PIN and a touch (`pinverification=1`, as sudo, polkit and the login greeter do), your password or your fingerprint. The key alone, without its PIN, unlocks nothing. The launcher's Sleep, the sleep key and a closed lid lock first (`vekrona-suspend`; `vekrona-lid.service` keeps logind from handling the lid and the sleep key itself while the session runs). A screen that cannot be locked holds a block lock on sleep (`vekrona-lock-guard.service`), so the machine stays awake with the session open and a record in the error list instead of suspending unlocked. The remaining gap is a suspend that something asks logind for directly, such as `systemctl suspend` in a terminal: swayidle's before-sleep hook tries to lock, but logind cannot cancel a suspend that has begun. Idle locks after 5 minutes. |
| Root | Any process running as you that wants root | sudo and polkit need the key's PIN and a touch, or the password. Every pam_u2f line reads the registration file `/etc/u2f_mappings`, owned by root with mode 0644, which a process of yours cannot rewrite: it cannot register a key of its own and sign in as you. (The old `~/.config/Yubico/u2f_keys` is never read again; `./install.sh 45` moves your line out of it once.) sudo has a PAM service of its own, `etc/pam.d/vekrona-sudo`, the stock one plus `XDG_SESSION_CLASS=none` so that `pam_systemd` opens no logind session for each sudo (a logind bug piles up closing sessions); authentication is unchanged (`etc/sudoers.d/50-vekrona-sudo-pam-service`). |
| Supply chain | Whoever can alter a package or download | Every dnf repo is GPG-checked against a vendored key whose fingerprint is pinned in `lib/common.sh` ([repo signing keys](agents.md#repo-signing-keys)). Each COPR repo and NVIDIA's CUDA repo also lists the packages it may provide (`includepkgs` in its repo file under `etc/yum.repos.d/`), so a compromised or expanded repo cannot replace a system package such as the kernel, glibc or the NVIDIA driver; RPM Fusion's driver comes from RPM Fusion alone. Downloads use `https` only, also after a redirect (`download_file`). Proton's unsigned RPMs are sha512-checked against their feed into a local repo. rune's unsigned RPM is fetched at a pinned release and checked against a pinned sha256 on a root-owned copy before dnf installs it. ScopeBuddy is fetched at a tag and checked against a pinned sha256. Flathub apps are Flatpaks signed by Flathub. Claude Code and the other agents you install yourself update themselves outside the snapshotted root, and nothing pins them. |
| LAN | Other machines on the same network (a cafe, a hotel) | firewalld's default zone is `public`, which holds exactly the services in `default_zone_services` (`lib/firewall.sh`): DHCPv6, Syncthing, Steam streaming and Steam LAN transfer (plus `ssh` on a test guest that carries `/etc/vekrona/keep-sshd`), and no port. Stage 40 closes everything else in it (stock `ssh` and `mdns`, AirPlay's 6001-6010, ports opened by hand), and stage 70 compares the zone with the same list. Fedora's workstation zone, which opens every port from 1025, is not used. There is no mDNS responder (`avahi` is removed) and systemd-resolved answers neither LLMNR nor mDNS (`etc/systemd/resolved.conf.d/50-vekrona.conf`), so the machine announces no name and listens on no multicast port. AirPlay is not supported. The Workstation leftovers that listened or ran as root without a use here are removed by stage 30: CUPS and its browser daemon, ModemManager, sssd, PackageKit, rsyslog, `nfs-utils` and `atd` ([packages vekrona removes](daily-use.md#packages-vekrona-removes)). Syncthing's local discovery broadcasts this machine's device ID every 30 s (UDP 21027), so the machine can be recognized on any LAN it joins. Any host of the network can announce devices of its own, with any addresses: Syncthing keeps an announced address as given and puts in the sender's address only for an unspecified one, and it looks up a host name that it is given (`registerDevice` in Syncthing's `lib/discover/local.go`). What such a host can make vekrona-sync's watcher do is bounded: it connects only to addresses that are IP literals of a private or link-local network (no loopback, no public address, no name), at most 4 for each of the 16 devices reported last, on 8 threads with a 1 s timeout, and it asks about at most one nearby device at a time, in a notification. |
| Tailnet | Other nodes on your tailnet, including a compromised one | Tailscale runs with shields up (`tailscale set --shields-up=true`): the node accepts no inbound connection from the tailnet, and its own outgoing connections and NAT traversal need no open port, so nothing here listens for the tailnet. The price: another node cannot start a connection to this machine over the tailnet, so a Syncthing peer cannot dial in (this machine dials out, or the LAN and relays carry it), Taildrop cannot deliver a file here and Steam Remote Play cannot reach this machine through the tailnet. Tailscale SSH is off (`--ssh=false`), so the tailnet cannot reach a shell either. Stage 40 sets both and stage 70 reads them back. tailscaled keeps no setting across a restart until the node is logged in, so a drop-in (`etc/systemd/system/tailscaled.service.d/vekrona-hardening.conf`) sets both again at every start; the first login is `tailscale up --shields-up --ssh=false`. |
| VPN and kill switch | Your ISP, the network you are on, a program that connects before the tunnel is up or after it drops | `vekrona-vpn` ([vpn](vpn.md)): WireGuard connections of NetworkManager behind an nftables table (`inet vekrona-vpn`, output and forward hooks) that is loaded before the tunnel comes up and stays until you turn the VPN off, so a dropped tunnel or a failed connect leaves traffic blocked, not leaking. What it lets through besides the tunnel: loopback, the tunnel's own packets (fwmark `0xca6c`, to the endpoint's address and port only), the local network except ports 53 and 853 (DNS and DNS over TLS go through the tunnel), Syncthing's local discovery, tailnet addresses on `tailscale0` plus `tailscaled`'s own packets (uid 0, never to the local network, to multicast or to ports 53 and 853), and the packets of the `toranon` user. Everything else is rejected, not dropped, so programs fail at once (IPv6 included, for a configuration without an IPv6 address). Root's part is `vekrona-vpn-apply@<op>-<uid>.service`, which polkit lets a `wheel` user start without a password (its scope is stated below), and which re-checks its instance name and its request file (regular file of that uid, no links, 1 MiB at most) and writes NetworkManager only a freshly rendered configuration. What it does not do: it is no boundary against a process of yours. That process can start those units, so it can import a configuration of its own and connect (all traffic then leaves through a tunnel it chose), or run `vekrona-vpn off` and so turn the kill switch off. In plain terms, the polkit rules (`50-vekrona-vpn.rules`, and `50-vekrona-tor.rules` for tor) let any process of a `wheel` user inside their `user@UID.service`, not only the one at the machine, start the apply units (`off` among them) and start and stop `tor.service`, all without a password; the kill switch has no unit of its own. The kill switch is also off after a reboot until you connect. Mullvad's private key lives in NetworkManager's root-only keyfile; the account number is typed once and not stored. |
| Tor Browser | A browser exploit in Tor Browser, a site that tries to learn your address, the person who gets a shell next to it | Its Flatpak has no network (`--unshare=network`): the only interface in the sandbox is `lo`, and the way out is a unix socket, `/run/tor-tb/socks` (`TOR_SOCKS_IPC_PATH`), of the system tor, in a directory owned by `toranon`, which an ACL opens to the group `vekrona-tor` (tor accepts a group-accessible socket directory only when its group is tor's own, so the directory's group cannot be `vekrona-tor`). You are in `vekrona-tor` and not in `toranon`; a new login applies the membership. A browser that cannot open a socket of its own cannot go around the proxy, so an exploit has no direct route to your address. The override also removes the PulseAudio socket (`--nosocket=pulseaudio`, so Tor Browser has no sound): pipewire-pulse runs as you with the network, and any client of its socket can make it open a connection to an address of its choice (`load-module module-tunnel-sink server=tcp:IP`, `module-rtp-send`); it has no switch to forbid that for one client (`pulse.allow-module-loading` is server-wide, as of pipewire 1.6), and turning it off for everyone would break the tests that load a null sink. What stays open: Flatpak lets every sandbox talk to the desktop portals, and the OpenURI portal opens an address in your default browser outside tor, so an exploited Tor Browser can make the host browser fetch a URL that names you (the file chooser, which downloads need, lives behind the same portal, so it stays); the Wayland socket (and X11 when there is no Wayland) is the sandbox's other way to the host, with no network in it. Tor Browser gets no control port (`TOR_PROVIDER=none`), and tor's control socket, its cookie and its data directory are not group-accessible (`ControlSocketsGroupWritable 0`, `CookieAuthFileGroupReadable 0` and `DataDirectoryGroupReadable 0` in `etc/tor/torrc.d/vekrona.conf`, which stage 70 reads back from tor's effective configuration), so the group hands no one control of tor. That costs the circuit display and New Identity (tor's `NEWNYM`); Whonix needs a filtering proxy for the control port, and vekrona has none. tor runs only while Tor Browser runs: `tor.service` is not enabled, `vekrona-tor-browser` starts it (polkit, as above) and stops it with the last Tor Browser. `vekrona-tor-browser install` downloads Tor Browser in the same sandbox, with no network either: the launcher can only use a TCP proxy, so a relay on the sandbox's own loopback (`lib/vekrona_tor_install.py`) hands its connections to that socket. tor has no TCP port on the host, so no local program can send traffic through tor around the kill switch, and the launcher's error dialogs that start another launcher process run it in a sandbox with no network too (and the install program closes them instead). tor bypasses the VPN (an `ip rule` for `toranon` and an exception in the kill switch), so Tor Browser's traffic does not go through the tunnel: your ISP sees that you use Tor, and your VPN provider does not see it. Tor Browser is still a program that runs as you: the Flatpak sandbox is what it is, not a VM. |
| Kernel | A process of yours, or one that escaped its sandbox, that wants kernel code or memory | `etc/sysctl.d/60-vekrona.conf` (stage 40, read back by stage 70): `kernel.yama.ptrace_scope=1` (a process attaches to its own children only, not to your other programs), `kptr_restrict=2` and `dmesg_restrict=1` (no kernel addresses, and `dmesg` needs sudo; `journalctl -k` still works), `kexec_load_disabled=1` (no other kernel until the next boot), `dev.tty.ldisc_autoload=0`, and no ICMP redirects or source routing on any interface. `etc/modprobe.d/vekrona-hardening.conf` makes modprobe run `/bin/false` for modules an unprivileged process can have loaded and this machine never needs: FireWire (DMA), SCTP, TIPC, ATM, the CAN protocols, and the JFFS2 and HFS filesystems. Only modules the Fedora kernel ships are listed, and `tests/stages/test-kernel-hardening.sh` fails on one it does not. `rp_filter` is left alone, because Tailscale and the WireGuard VPN (`vekrona-vpn`) break with strict mode. |
| Disk | Someone with the powered-off machine | LUKS root, unlocked by password or by a FIDO2 key with PIN and touch ([sign-in](sign-in.md)). |

## The `input` group

Your user is not in the `input` group. `xremap-wlroots` runs as a system service under its own user, `xremap`
(`etc/systemd/system/xremap.service`), and that user alone reads the keyboards. So a process running as you cannot log the key
presses on the machine, including the password typed on the lock screen, and cannot inject key events: the udev rule
`etc/udev/rules.d/70-vekrona-uinput.rules` takes the seat's access to `/dev/uinput` away, so only `input` (that is, xremap) may open it.
xremap's config is root's copy, `/etc/xremap/config.yml`, because a config you could write would run commands as the xremap user.

What this costs: a program that needs raw input devices (an input remapper, a game controller tool that opens `/dev/input/event*`) now
needs `sudo` or an ACL you grant on purpose.

## When you change something here

A new listener on a local port, a new place that copies untrusted text into an agent prompt, a new
secret file, or a new way to reach root belongs in the table above in the same commit.
